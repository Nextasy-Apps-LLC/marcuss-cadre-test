# compound-review

Reviews one dev PR against the issue it closes. The reviewer never pushes
fixes and never moves the board — the issue stays **In Review** until Marcus
merges and runs `compound-done`.

## Steps

1. **Load the contract.** Read the PR (diff, body, linked issue via the
   `Closes #<n>` reference) and the issue's Technical spec, Acceptance
   criteria, and Applicable learnings sections.
2. **Review** — either directly or by spawning the `compound-reviewer` agent
   with the PR number, issue number, and repo — across all five dimensions it
   defines: spec adherence (criterion by criterion), correctness, test quality
   (TDD evidence + e2e genuinely hitting real endpoints), repo conventions
   (scoped CLAUDE.md files of touched dirs), and KB-gotcha compliance (cite
   file/lines for each Applicable-learnings entry).
3. **Check the learnings side:** the PR body must either link a learnings PR
   (stacked on this branch, touching only `kb/learnings.json`) or state "no
   new learnings". A silent omission is a blocker — the standing acceptance
   criterion says so.
4. **Post ONE review** via GitHub MCP `pull_request_review_write` (use
   `create` → `add_comment_to_pending_review` for line comments →
   `submit_pending`; a single `create`-and-submit for verdict-only reviews).
   The review body leads with exactly one verdict:
   - **APPROVE** → submit as APPROVE.
   - **APPROVE WITH MINOR COMMENTS** → submit as COMMENT, minors listed,
     each explicitly marked non-blocking.
   - **REJECT — BLOCKERS** → submit as REQUEST_CHANGES, blockers itemized
     with file/line and what "fixed" looks like.

   End the review body with the attribution footer:

   ```
   ---
   _Generated by [Claude Code](https://claude.ai/code)_
   ```

5. Reply in chat with the verdict and the two or three findings that matter
   most. Do not comment further on the PR beyond the single review.
